# Переводы через T-Bank MCP

## Инструменты

| Тул | Что делает |
|---|---|
| `list_accounts()` | Список счетов пользователя (источник) |
| `account_requisites(account_id)` | Реквизиты счёта (номер, БИК) — чтобы ПРИНЯТЬ перевод, а не отправить |
| `transfer_sbp_resolve(phone)` | **Резолвинг получателя по номеру (read-only, БЕЗ денег).** Возвращает всё, куда можно заплатить по этому номеру: счёт получателя в Т-Банке + его банки в СБП (маскированное имя + банк + isDefaultBank + bankMemberId/pointerLinkId). ОБЯЗАТЕЛЬНО для НОВОГО (несохранённого) получателя перед комиссией/переводом |
| `payment_commission(body)` | Предпросмотр комиссии (БЕЗ денег) |
| `payment_qr(qr)` | **Разбор платёжного QR со счёта (read-only, БЕЗ денег).** Строка вида `ST00012\|Name=…\|PersonalAcc=…`. Печатает получателя, реквизиты, сумму и комиссию — то, что показываешь пользователю ПЕРЕД оплатой |
| `transfer_requisites(amount, qr, comment, account_number, bik, inn, name, kpp, corr_account, bank_name, nds, personal_account, from_account, force)` | Перевод юрлицу/ИП по реквизитам. РЕАЛЬНЫЕ ДЕНЬГИ |
| `transfer(amount, to_account, description, provider, bank_member_id, masked_fio, pointer_link_id, from_account, force)` | Перевод (подпись внутри). phone/СБП по умолчанию. Получатель резолвится АВТО-если поля не переданы. `provider="transfer-inner"` (между своими счетами) НЕ реализован — тул откажет |

## Флоу

### Шаг 1: Определить тип перевода

| Пользователь сказал | Тип | `provider` |
|---|---|---|
| «переведи на +7XXXXXXXXXX» / «по СБП» | P2P по телефону (СБП) | `p2p-anybank` (по умолчанию) |
| «переведи между счетами» | Между своими счетами | `transfer-inner` (не автоматизировано — приложение) |
| «переведи по реквизитам …» (БИК/счёт/ИНН), «оплати счёт компании», QR со счёта | Юрлицо / ИП | **`transfer_requisites`** — отдельный тул, не `transfer` |

Если не указан — уточни: «Перевод по телефону (P2P) или по номеру счёта?»

### Шаг 2: Найти счёт-источник

1. Вызови `list_accounts()` — показать счета с балансами.
2. Если у пользователя один счёт с деньгами — выбери его.
3. Если несколько — спроси: «С какого счёта: Current (2751₽) или Credit (доступно 50000₽)?»
4. Запомни `account_id` источника.

### Шаг 3: Резолвинг получателя (phone — ОБЯЗАТЕЛЬНО для нового получателя)

Для перевода по телефону нужно знать, куда именно платить. Вызови
`transfer_sbp_resolve(phone)` (read-only, без денег):
- Вернёт по кандидату две строки: `И. И. | Банк ★ДЕФОЛТ`, а под ней
  `providerFields: {…}` — JSON, внутри которого и лежат `bankMemberId` и
  `pointerLinkId`. Отдельными полями в строке они НЕ печатаются, бери их из этого
  JSON.
- **Счёт в Т-Банке** — отдельный кандидат, помечен `← счёт в Т-Банке, перевод
  внутри банка (без СБП)`. У него **нет `bankMemberId`** — так и должно быть.
  Переводить на него: `pointer_link_id` передай, `bank_member_id` оставь пустым.
  Это обычно самый быстрый и предсказуемый вариант, но выбор всё равно за
  пользователем.
- **Несколько кандидатов без дефолта** — выбирает пользователь, не ты (перевод не
  в тот банк = деньги не туда). Если ты уже вызвал `transfer` без
  `pointer_link_id`, он покажет пикер банков сам — тогда ничего не спрашивай. Если
  резолвил заранее через `transfer_sbp_resolve` — спроси текстом и запомни выбранный
  `pointer_link_id` (+ `bank_member_id` и `masked_fio`, если это банк СБП). Выбор
  банка — это «куда», а не «да»: сумму всё равно подтвердит отдельная кнопка.
- **Пусто** — у номера нет счёта в Т-Банке и он не зарегистрирован в СБП (или
  неверный). Скажи пользователю, перевод невозможен.
- Для **сохранённого** получателя (есть в `get_data("templates")` /
  `get_data("contacts")`) поля можно взять оттуда — резолвинг необязателен, но
  `transfer_sbp_resolve` работает всегда.

**Не подменяй резолвинг комиссией.** `payment_commission` без `pointerLinkId`
отвечает «Комиссия не взимается» и `"unfinishedFlag": true` для любого номера —
это «получатель не определён», а не «получатель найден и перевод бесплатный».
Единственный ответ про наличие счёта в Т-Банке — список из
`transfer_sbp_resolve`.

### Шаг 4: Проверить комиссию (ОБЯЗАТЕЛЬНО до перевода)

Вызови `payment_commission(body)` с `payParameters` (зеркало тела перевода — с
разрешёнными полями получателя, **не** `pointerType:ACCOUNT`, который банк отвергает):
```json
{
  "payParameters": {
    "account": "<account_id источника>",
    "moneyAmount": 1500,
    "currency": "RUB",
    "paymentType": "Transfer",
    "provider": "p2p-anybank",
    "providerFields": <providerFields из transfer_sbp_resolve — НЕ пиши pointerType/8276 руками>
  }
}
```
Получишь комиссию + описание. Покажи пользователю.

### Шаг 5: Показать детали (подтверждает — кнопка тула, не ты)

Покажи ВСЕ данные — их не будет на кнопке:
```
Перевод:
  Откуда: Current (2751 ₽)
  Куда: +7XXXXXXXXXX
  Сумма: 1500 ₽
  Комиссия: 0 ₽ (бесплатно)
  К зачислению: 1500 ₽
```

Дальше сразу вызывай `transfer` — **не спрашивай «да/нет» текстом**. Тул сам
покажет пользователю кнопки «Перевести 1 500 ₽ → И. И. · Банк?» / «Отмена» и
отправит платёж только после нажатия. Твой текст выше — про то, чего на кнопке
нет (счёт списания, комиссия, к зачислению); согласие даёт кнопка.

Если пользователь нажал «Отмена» или окно закрылось — тул вернёт это текстом,
деньги на месте. Не переспрашивай и не вызывай повторно сам: следующий перевод —
по новой просьбе пользователя.

### Шаг 6: Перевод

Вызови `transfer(amount, to_account, description, ...)`:
- `amount` — сумма в рублях (число)
- `to_account` — телефон (`+7XXXXXXXXXX`) для phone/СБП
- `description` — сообщение получателю (он его увидит)
- **`from_account` — счёт списания из Шага 2.** Если пользователь выбирал счёт,
  передавай его обязательно: без этого аргумента спишется с первого рублёвого
  Current с положительным балансом, а не с выбранного.

**phone (по умолчанию):** если передать `pointer_link_id` (+ `bank_member_id`/`masked_fio`
для банка СБП; для счёта в Т-Банке `bank_member_id` пустой) — перевод пойдёт туда, куда
выбрал пользователь. Если **не** передать — `transfer` резолвит получателя автоматически и
выберет дефолтного кандидата (или единственного); при нескольких без дефолта вернёт
`RECIPIENT_MULTIPLE_BANKS` со списком — тогда передай выбранные поля явно.
**Между своими счетами (`provider="transfer-inner"`):** через MCP не делается,
используй приложение.
**По реквизитам юрлица (БИК/счёт/ИНН):** это НЕ `transfer` — см. отдельный флоу ниже.

**«Перевод НЕ выполнен»** — запрос до банка не дошёл или банк его отклонил.
Деньги на месте, ничего не заблокировано: исправь причину (например, выбери банк
получателя) и повтори обычным вызовом, `force` не нужен.

**Если ответ начинается с «ИСХОД НЕИЗВЕСТЕН»** — запрос ушёл, но подтверждения нет.
Деньги могли списаться. НЕ повторяй: проверь `list_operations(from_account, days=1)`.
Перевода нет — только тогда `transfer(..., force=True)`, и он переиспользует тот же
идентификатор платежа, чтобы банк распознал повтор, а не создал второй перевод.
Повторный вызов без `force` тул заблокирует сам.

### Шаг 7: Отчёт

```
✅ Перевод выполнен
  Сумма: 1500 ₽
  Получатель: +7XXXXXXXXXX
  Комиссия: 0 ₽
  Остаток на счёте: 1251 ₽
```

При ошибке — покажи код ошибки + предложи варианты.

## Флоу: перевод юрлицу или ИП по реквизитам

Счёт от компании, оплата поставщику, аренда на расчётный счёт. Тул отдельный —
`transfer_requisites`, у него девять полей реквизитов, в `transfer` они не помещаются.

### Если есть QR со счёта

1. `payment_qr(qr)` — строка целиком, как её прочитала камера
   (`ST00012|Name=ООО …|PersonalAcc=…|BIC=…|Sum=…`). Тул печатает получателя,
   ИНН/КПП, счёт, банк, БИК, сумму из QR и комиссию. **Сумма в QR — в копейках,
   тул уже перевёл её в рубли; не пересчитывай сам.**
2. Если тул сказал, что это не перевод по реквизитам, а другой провайдер — это
   счёт за услугу: дальше `payment_providers(provider_id=…)` и `pay_bill(...)`.
3. Покажи всё пользователю — получателя, реквизиты, назначение, сумму. Текстом
   «да» не жди: подтверждение даст кнопка на шаге 4.
4. `transfer_requisites(amount=…, qr="<та же строка>", comment="…")` — тул покажет
   «Перевести N ₽ → ООО …?» и отправит только после нажатия.

### Если реквизитов нет в QR — руками

`transfer_requisites(amount=…, account_number="4070…" (20 цифр), bik="0445…"
(9 цифр), inn="…" (10 или 12 цифр), name="ООО …", comment="…")`.
`corr_account` и `bank_name` подтянутся по БИК сами — не спрашивай их у пользователя.

### Назначение платежа — сначала прочитай, потом спрашивай

`comment` банк ТРЕБУЕТ, без него тул откажет до отправки. Но спрашивать
пользователя — последний шаг, а не первый. Ищи в таком порядке:

1. **В самом QR.** Ключ `Purpose` уже разбирается в `comment` — если `payment_qr`
   напечатал строку «Назначение платежа: …», ничего больше делать не надо.
2. **В счёте**, если пользователь прислал фото, скан или PDF — прочитай его.
   Оттуда берутся все три вещи сразу: номер и дата счёта, за что платим, и есть
   ли НДС. Формулируй как в деловой практике:
   `Оплата по счету № 42 от 01.08.2026 за материалы. В том числе НДС 20% — 3933.33 руб.`
   или `… Без НДС.` **Сумму НДС не считай сама — переноси из счёта как есть.**
   Не влезает в 160 символов — сокращай хвост, номер и дату счёта оставляй.
3. **В переписке.** «Оплати аренду за август» — уже назначение; уточни только
   номер счёта, если он где-то был.
4. **И только теперь спроси** — коротко и конкретно: «За что платим? Нужны номер
   и дата счёта».

Никогда не сочиняй назначение сам. «Оплата услуг» вместо реального номера счёта
получателю не поможет разнести платёж, а банк такую строку пропустит.

### Остальное

- **НДС** (`nds`) — **оставляй по умолчанию `"322"`, даже если счёт с НДС.**
  Выглядит контринтуитивно, поэтому запомни, где НДС на самом деле: он живёт в
  **тексте назначения**, отдельной строкой с суммой — как в примере выше, — а не в
  этом поле. Банк и сам подставляет `322`, отвечая на QR со счётом с НДС.
  `"323"` («НДС включен») передавай только если пользователь прямо просит эту
  отметку: банк, судя по всему, дописывает НДС-строку сам, и вместе с твоей она
  задвоится.
- **Счёт списания** (`from_account`) — если у пользователя их несколько.

### Чего не делать

- Не подставляй КПП, если его нет: у ИП его не бывает, поле необязательное.
- Не «исправляй» счёт получателя и не дополняй его нулями. Ошибка в 20-значном
  счёте оплачивает чужой счёт, и вернуть это сложнее, чем перевод по телефону.
- Ответы «ИСХОД НЕИЗВЕСТЕН» и «ПОВТОР ЗАБЛОКИРОВАН» обрабатывай так же, как у
  `transfer`: проверить `list_operations`, и только потом `force=True`.

### Если банк ответил «ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ» (WAITING_CONFIRMATION)

Крупный перевод (например, юрлицу по реквизитам) банк принимает, но держит до
второго фактора. Деньги **ещё не ушли**, но платёж уже висит на стороне банка.

- **Не повторяй** `transfer` / `transfer_requisites` — новый вызов создаст ВТОРОЙ
  висящий платёж (id списания переиспользуется только при `force=True`).
- Возьми у пользователя код из SMS или подтверждение из пуша и вызови
  `confirm_payment(attempt_id, otp)`, где `attempt_id` — из ответа «ТРЕБУЕТСЯ
  ПОДТВЕРЖДЕНИЕ». Это НЕ `confirm_otp` (тот — только для логина).
- Кнопка «Перевести/Отмена» уже была ДО отправки — этот шаг про второй фактор
  банка, а не про повторное согласие. КОД кнопкой не ввести (в клиенте нет
  текстового поля): бери его у пользователя текстом и передавай
  `confirm_payment(attempt_id, otp='<код>')`.
- Не ушли ли деньги — `payment_status(attempt_id)` или `list_operations(days=1)`.
- Неверный код не двигает состояние: платёж остаётся висящим, можно ввести заново.
- Код нигде не логируется — ни в трейсе, ни в журнале попыток.

## Правила

1. **Всегда проверяй комиссию** перед переводом — даже если бесплатная.
2. **Подтверждает кнопка тула, а не твой вопрос.** `transfer` и
   `transfer_requisites` сами показывают пользователю «Перевести N ₽ → кто?» с
   кнопками и отправляют платёж только после нажатия. Твоя часть — ДО вызова:
   назвать счёт списания, комиссию, реквизиты и назначение (их на кнопке нет).
   Своё «да/нет» текстом не спрашивай — это второй вопрос об одном и том же.
   Уточняющие вопросы («по телефону или по реквизитам?», «с какого счёта?», «за
   что платим?») — можно и нужно: это «куда» и «сколько», а не согласие.
   Клиент без элиситации получит «ПЛАТЁЖ НЕ ВЫПОЛНЕН» — не обходи это и не
   изобретай текстовое подтверждение; объясни пользователю, что платить нужно из
   клиента с кнопками (Hermes/Telegram, Claude Code) или в приложении.
3. **Сумма — число** (1500, не "1500 рублей").
4. **Получатель** — телефон в формате `+7XXXXXXXXXX` (11 цифр, +7…) или счёт.
5. **P2P по телефону** — дефолтный вариант.
6. **Не переводи с кредитки** без явного согласия (комиссия + проценты).
