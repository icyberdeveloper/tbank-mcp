# Заказ продуктов через T-Bank MCP

Этот скилл направляет агента через процесс заказа продуктов через T-Bank MCP (Город).
MCP обращается к реальным магазинам Т-Банка — реальные деньги, реальная доставка.
Состав корзины всегда показывай пользователю перед оплатой; сумму подтвердит сам
`grocery_checkout` — кнопкой, текстом «да» её не спрашивай.

> ⚠️ **Зависимость рантайма:** `grocery_checkout` выполняет web-checkout через
> **Playwright + chromium**. Если они не установлены, заказ упадёт с ошибкой Playwright.
> Поставь один раз: `python -m playwright install chromium` (в окружении MCP). Если
> пользователь жалуется на ошибку браузера/checkout — сначала проверь это.

## Инструменты MCP (в порядке использования)

| Тул | Что делает |
|---|---|
| `grocery_stores(sort_by, order)` | Доступные магазины: appId, pointId, окно ближайшей доставки, её цена, минимальная сумма, кешбэк. **Источник appId/pointId для всех остальных тулов.** `sort_by` ∈ `speed` \| `price` \| `min_sum`; пусто — порядок банка. |
| `grocery_search(query, app_id, point_id, limit)` | Поиск товара по названию — возвращает товары с тегом `likely_raw`. **app_id/point_id обязательны.** Шапка говорит «показано X из Y»; `limit=0` — все, что попали в выборку. Если шапка пишет «выборка упёрлась в потолок» (или так на ПУСТОЙ выдаче) — совпадение может быть за горизонтом: уточни запрос, это не «нет в магазине». |
| `grocery_rank(query, app_id, point_id, sort_by, order, limit, with_nutrition)` | Кандидаты с атрибутами (цена, вес, КБЖУ), опционально отсортированные. Стратегию задаёшь ты — см. Шаг 4. Без `sort_by` — порядок магазина. |
| `grocery_good_info(good_id, app_id, point_id)` | Карточка товара: состав, КБЖУ на 100 г и на упаковку, срок хранения, производитель. |
| `grocery_plan_order(ingredients, app_id, point_id)` | Умный планировщик: ищет каждый ингредиент (сначала custom_ordered, потом глобально) → план. Каждая позиция помечена `✓` или **`⚠ проверь`** (совпало не полностью — сверь по имени). Синонимы/транслит не угадывает — добирай лесенкой Шага 3b. **app_id/point_id обязательны.** |
| `grocery_add_to_cart(items, app_id, point_id)` | **Прибавить** товары к корзине (адрес доставки берётся сам). **app_id/point_id обязательны.** Строку, у которой итоговое количество выше остатка (`countAvailable`), отклоняет с `CART_QUANTITY_CONFLICT` и НИЧЕГО не пишет — не clamp'ит молча. |
| `grocery_set_cart(items, app_id, point_id, clear)` | **Задать** количество точно: `count=0` убирает товар, `clear=True` очищает корзину. Возвращает состав ПОСЛЕ изменения. Количество выше остатка — отказ `CART_QUANTITY_CONFLICT` (запись не идёт; количество автоматически не уменьшается). |
| `grocery_cart(app_id, point_id)` | Получить содержимое корзины (проверить перед оплатой). **Те же app_id/point_id что в add_to_cart.** Показывает «в наличии N» по строкам и блок `CART_QUANTITY_CONFLICT`, если запрошено больше остатка — тогда вместо подсказки на checkout стоит «сначала устрани расхождение». |
| `grocery_checkout(app_id, point_id, force, account_id, expected_sum, dry_run)` | Полный чекаут: web-корзина → доставка → заказ → оплата. РЕАЛЬНЫЕ ДЕНЬГИ. **Те же app_id/pointId.** Если корзина просит больше остатка — останавливается ДО доставки (`CART_QUANTITY_CONFLICT`, называет SKU), заказ не создаётся и деньги не двигаются. Иначе сам узнаёт финальную сумму, показывает пользователю кнопку «Оформить заказ на N ₽?» и оформляет ровно на неё — текстом «да» не спрашивай. `dry_run=True` — предпросмотр без заказа и без денег, необязательный: для того чтобы назвать итог и слот заранее (работает и там, где кнопок нет). `expected_sum` — необязательная сверка с суммой из предпросмотра; расхождение печатается на кнопке. Счёт по умолчанию — тот, которым платили за продукты в приложении; `account_id` его переопределяет. `force=True` — повтор после UNKNOWN, только если пользователь подтвердил, что прошлого заказа нет (Шаг 8, пункт 5); кнопка при повторе показывается снова. |
| `grocery_attempts()` | Read-only: недавние попытки checkout (status, order_id, attempt_id) — для reconciliation после UNKNOWN. |
| `grocery_order_status(order_id, app_id)` | Read-only: статус заказа на бэкенде по orderId — проверь, создался/оплатился ли после UNKNOWN. **`app_id` обязателен** (тот же, что в checkout), хоть в схеме и выглядит опциональным — без него банк ответит сырым 400. |
| `grocery_order_cancel(order_id, app_id)` | Отмена оформленного заказа (оплаченного тоже — деньги вернутся на счёт списания). С `app_id` сам перечитает заказ и покажет фактический статус. |

> ⚠️ **app_id и point_id обязательны во всех grocery-тулах кроме `grocery_stores`.** Без них тул
> вернёт `NO_STORE_CONTEXT`. Дефолтный магазин вслепую НЕ подставляется — иначе корзины
> add_to_cart / cart / checkout разъедутся по разным магазинам. Каждый ответ начинается с
> `[store appId=… pointId=…]` — сверяй, что магазин тот же. Если увидишь `CART_CONTEXT_MISMATCH` —
> контекст рассинхронизирован, перечитай `grocery_stores()` и передай согласованные appId/pointId.

## Флоу (всегда в таком порядке)

### Шаг 1: Определить что заказывать

**Если пользователь называет блюдо** (борщ, оливье, плов и т.д.):

1. Попробуй определить ингредиенты из своих знаний (LLM). Для популярных блюд
   (борщ, оливье, плов, паста, блины, котлеты, супы) — этого достаточно.

2. **Если блюдо незнакомое или необычное** — используй WebSearch:
   ```
   WebSearch("рецепт {название блюда} ингредиенты список")
   ```
   Найди рецепт → извлеки список ингредиентов из результата.
   Если результатов несколько — возьми первый подходящий (eda.ru, povarenok.ru,
   championat.com, gastronom.ru — авторитетные кулинарные сайты).

3. Покажи пользователю полный список. Если пользователь что-то назвал, а ты по
   рецепту знаешь что ещё нужно — **скажи прямо**:
   «Для борща нужно: свёкла, говядина, капуста, морковь, лук, чеснок,
   картофель, томатная паста. Ты не назвал свёклу и морковь — они основные!
   Добавить их?»
   Дождись подтверждения финального списка.

**Если пользователь перечисляет ингредиенты сам** (не называет блюдо):

1. Сравни с известными рецептами — не пропустил ли пользователь что-то важное.
   Примеры типичных забытых ингредиентов:
   - Борщ: часто забывают свёклу, томатную пасту, уксус/лимон (для цвета)
   - Оливье: часто забывают морковь, горошек, огурцы, майонез
   - Плов: часто забывают чеснок, зиру, барбарис, нут
   - Картофельное пюре: часто забывают молоко/масло
   - Паста: часто забывают пармезан, оливковое масло
   - Блины: часто забывают молоко, яйца, масло

2. Если не уверен в полноте списка (блюдо не знакомо) — WebSearch:
   ```
   WebSearch("{названные ингредиенты} что за блюдо рецепт")
   ```
   Определи блюдо → найди полный рецепт → сравни с тем что пользователь назвал.

3. Если чего-то не хватает — **не просто предложи, а укажи прямо**:
   «Вообще-то в рецепт ещё входят огурцы и морковка! Добавить?»
   Будь как знающий друг — если забыт основной ингредиент (свёкла для борща),
   скажи об этом с акцентом: «Свёкла — это ОСНОВНОЙ ингредиент борща!»

4. Если пользователь сказал «закажи продукты для борща, но только говядину и картошку»
   (сознательно урезал) — НЕ настаивай, просто подтверди: «Заказываю только говядину
   и картошку. Остальное пропускаю. Верно?»

5. Дождись подтверждения финального списка.

### Шаг 2: Выбрать магазин

> **Список длинный или смешанный (видны сигналы конфликта сетей)? Не выбирай магазин
> здесь.** Иди в **[Флоу: длинный или смешанный список](#флоу-длинный-или-смешанный-список)** —
> там магазин выбирается по ПОКРЫТИЮ списка (probe), а не по скорости, и только потом
> фиксируется. Заказ, собранный в неверном магазине, кросс-магазинными «дозаказами» уже
> не чинится дёшево.

1. Вызови `grocery_stores()` — увидеть доступные магазины.
2. Покажи пользователю топ 3-5: название, время доставки, минимальная сумма заказа, кешбэк %, но только если просит.
3. **Главный критерий — ассортимент, а не скорость.** Магазин, где список НЕ собирается
   целиком, тянет за собой второй заказ и вторую доставку — это дороже любой экономии на
   скорости. Скорость, цена доставки и минимум решают только при прочих равных — между
   магазинами, которые покрывают список одинаково.
4. **Затем приоритет** — магазины, где пользователь уже заказывал (есть категория
   `custom_ordered`), потом самая быстрая доставка + низкий минимум.
5. Запомни выбранные `appId` и `pointId` — передавай их во все последующие вызовы.
6. **Смена магазина после сборки корзины — не бесплатна:** id товаров у каждой сети свои,
   корзина привязана к `appId+pointId`, и первая же запись в другой магазин СТИРАЕТ
   собранную корзину (бэкенд держит одну корзину на всех). Поэтому магазин выбирается
   ОДИН раз, до сборки.

### Шаг 3: Поиск ингредиентов

**a. Вызови `grocery_plan_order(ingredients_list, app_id, point_id)`** — один вызов ищет всё:
- Сначала ищет в `custom_ordered` («Вы заказывали») — товары которые пользователь покупал раньше.
- Потом глобальный поиск (`search/fulltext` с `inStockFilter` — только в наличии).
- Возвращает: `{items, total_sum, missing}`. Каждая позиция помечена `✓` или **`⚠ проверь`**.

**`⚠ проверь` — это НЕ найдено, это «нашёл, но, похоже, не то».** Тул матчит по токенам
и при неполном совпадении честно предупреждает (кетчуп «с помидорами» на запрос
«помидоры», куриный фарш на «фарш индейки»). **Сверься глазами по имени** и, если не то,
прогони позицию по лестнице ниже как missing. Не клади `⚠` в корзину вслепую.

**b. Если позиция `MISSING` или `⚠ проверь`** — сначала выжми ТЕКУЩИЙ магазин, и только
потом думай про замену. `MISSING` — это НЕ приговор «нет в магазине»: детерминированный
матчинг MCP чинит пунктуацию (бэктик в `Lay\`s`), порядок слов и словоформы, но
**синонимы, транслит и опечатки он намеренно НЕ угадывает — это твоя работа через веб.**
Лестница по каждой такой позиции:

1. `grocery_search("свёкла", app_id, point_id)` — прямой поиск. Результаты
   отсортированы: `likely_raw: true` (сырое) сначала. **Предпочитай сырое**, если
   пользователь не просил готовое.
2. **Свои варианты** (ты их знаешь): транслит латиница↔кириллица (`сникерс`→`snickers`,
   `лейс`→`lay's`, `кола зеро`→`coca-cola`), очевидный синоним (`помидоры`→`томаты`,
   `сгущёнка`→`сгущённое`), одиночный токен, снять бренд/уточнение.
3. **`WebSearch`, когда своих не хватает** — для точного названия на витрине, редкого
   бренда, опечатки: поиском по запросу «<товар> <сеть> точное название» или
   «<бренд> как пишется на этикетке», вытащи кандидат-токены → повтори `grocery_search`.
   Веб часто знает точное написание с этикетки, которого нет в разговорном названии.
4. **Браузинг категории** — крайняя мера, когда бренд-запрос пуст: поищи по категории
   (`grocery_search("чипсы", ...)` с `limit=0`) и найди бренд глазами в выдаче: товар,
   который не находится по бренду, обычно лежит в категории под другим названием.
5. **«Выборка упёрлась в потолок»** в шапке — совпадение может быть за горизонтом: уточни
   запрос (это не «нет в магазине»).

**Только если и веб, и браузинг пусты — позиция реально отсутствует** в этом магазине.
Тогда либо аналог (WebSearch «аналог/замена <товар>»), либо она уходит в общий список
нерешённого (Шаг 5).

**Если пользователь говорит «я вижу это в приложении, а ты не находишь»** — сначала
пройди лесенку (частая причина — пунктуация/транслит, как бэктик в `Lay\`s`). Если и после
неё пусто — честно скажи, что in-stock выдача API этой точки могла отстать от родного
приложения; предложи проверить наличие в приложении.

Что НЕ делать здесь: не спрашивай пользователя «заменить или другой магазин?» по каждой
позиции по ходу. Это уводит из магазина с ещё нерешёнными позициями и плодит заказы.
**Копи всё нерешённое в ОДНУ таблицу** и вынеси одним вопросом — см. Шаг 5.

### Шаг 4а: Стратегии выбора МАГАЗИНА

То же правило, что и для товара: сортируй, только если пользователь назвал критерий.
Не назвал — бери порядок банка (он уже учитывает, чем человек пользуется).

| Что сказал пользователь | Вызов |
|---|---|
| ничего про магазин не сказал | `grocery_stores()` без `sort_by` |
| «побыстрее», «самая быстрая доставка», «надо срочно», «привезите сегодня» | `grocery_stores(sort_by="speed")` |
| «где доставка дешевле», «без платы за доставку» | `grocery_stores(sort_by="price")` |
| «у меня маленький заказ», «не хочу набирать на 2000» | `grocery_stores(sort_by="min_sum")` |

Что надо понимать про скорость, прежде чем что-то обещать пользователю:

- **Банк отдаёт слоты двух разных видов.** Одни относительные — «до 15 мин»,
  «20–35 мин» (Самокат, Пятёрочка, ВкусВилл). Другие абсолютные — «завтра
  08:00–11:00» (METRO, Ашан, О'КЕЙ, вся крупная розница). Тул сортирует по **концу**
  окна, то есть по «привезут не позже», — только это число и сравнимо между двумя
  видами.
- **Магазины без слота уходят в конец** — и при `asc`, и при `desc`. «Срок не
  указан» это не «мгновенно».
- **Быстро ≠ дёшево и ≠ доступно.** У самого быстрого может быть минимальная сумма
  выше твоей корзины или платная доставка. Показывай пользователю всю строку —
  окно, цену доставки и `minSum`, — а не только «самый быстрый — Самокат».
- **Ассортимент решает выбор магазина, скорость — только при прочих равных.** Это правило
  ДО сборки, а не оправдание после: сначала пойми, где список собирается целиком (для
  длинного/смешанного списка — probe из
  [Флоу: длинный или смешанный список](#флоу-длинный-или-смешанный-список)), потом среди
  покрывающих магазинов бери тот, что быстрее/дешевле. Смена магазина после
  сборки обнуляет корзину (id товаров у каждой сети свои, бэкенд держит одну корзину),
  так что если пользователь просит «побыстрее», когда корзина уже собрана, — скажи, что
  придётся пересобирать, и спроси.

### Шаг 4: Стратегии выбора товара

> **Главное правило: стратегия применяется только по прямому запросу пользователя.**
> Не подставляй «самое дешёвое» или «минимум калорий» по своей инициативе — если
> человек просто попросил купить творог, он хочет творог, а не оптимум по какой-то
> метрике. Без явного критерия вызывай `grocery_rank` **без `sort_by`** и бери
> порядок магазина (или `grocery_plan_order`, который сначала смотрит в
> `custom_ordered` — ранее заказанное).

`grocery_rank(query, app_id, point_id, sort_by, order, limit, with_nutrition)` —
это механизм, а не политика. Он умеет сортировать по одному полю; какое поле и в
какую сторону — решаешь ты по формулировке пользователя.

| Что сказал пользователь | Вызов |
|---|---|
| ничего про выбор не сказал | `grocery_rank(q, ...)` без `sort_by` |
| «подешевле», «самое дешёвое», «сэкономь» | `sort_by="price"` |
| «получше», «премиум», «не экономь» | `sort_by="price", order="desc"` |
| «полегче», «поменьше калорий», «на диете» | `sort_by="kcal"` |
| «самое калорийное», «посытнее» | `sort_by="kcal", order="desc"` |
| «побольше белка», «протеин» | `sort_by="protein", order="desc"` |
| «без жира», «обезжиренное» | `sort_by="fat"` |
| «поменьше углеводов», «кето» | `sort_by="carb"` |
| «побольше объём», «большую упаковку» | `sort_by="weight", order="desc"` |

Дальше — то, что тул за тебя не сделает:

| Стратегия | Как применить |
|---|---|
| **Цена за кг** | Веса разные: «Картофель 2.8 кг за 160 ₽» = 57 ₽/кг, а «Картофель 1 кг за 120 ₽» = 120 ₽/кг. `sort_by="price"` сортирует по цене упаковки, а не за килограмм — для честного сравнения возьми `price` и `weight` из выдачи и посчитай сам. |
| **Калорийность порции, а не 100 г** | `kcal` — на 100 г, `kcal_pack` — на всю упаковку. Для «что съесть на 300 ккал» нужен `kcal_pack`. |
| **Лучшее качество** | Предпочитай собственные марки магазина («Просто Азбука», «Наша Ферма») — обычно свежее. Цена тут плохой прокси. |
| **Конкретный бренд** | Просто в запрос: `grocery_rank("Borges оливковое масло", ...)`. |
| **Бюджет на всё блюдо** | Считай сумму выбранных позиций. Превысил — покажи размен: «Говядина Orenbeef 2473 ₽ vs обычная 1200 ₽, разница 1273 ₽. Меняем?» |
| **Из ранее заказанного** | `grocery_plan_order` первым делом смотрит `custom_ordered`. |

Про `with_nutrition`: КБЖУ подтягивается автоматически, когда сортируешь по
питательному полю. Это +1 запрос на кандидата, поэтому не проси его без нужды.
Детали одного товара (состав, срок хранения, производитель) — `grocery_good_info`.

**Прочерк в КБЖУ — это «сеть не опубликовала», а не «ноль».** Такие товары всегда
уходят в конец списка, в обе стороны сортировки. Не выдавай их за низкокалорийные.

**Перед тем как сказать «КБЖУ не указано» — прочитай «Описание:» в ответе
`grocery_good_info`.** У части товаров структурного поля с БЖУ нет, но сеть
пишет его текстом прямо в описании («белки 3 г, жиры 2 г, углеводы 12 г» или
похожей формулировкой) — это то же самое значение, просто в другом месте
ответа, а не «сеть ничего не публикует».

### Шаг 5: Обработка отсутствующих товаров

Сюда попадают только позиции, что не сдались лестнице из Шага 3b. Собери их в ОДНУ
таблицу и вынеси одним вопросом — не по одной по ходу. Порядок вариантов принципиален:
**замена в этом магазине → другой магазин → пропуск последним**. Пропуск — худший исход
(пользователь не получает то, что просил), поэтому это крайняя мера, а не средний вариант.

1. **Батч, а не по одной.** Одна таблица: строка × конкретная замена (с id и ценой) ×
   вариант. Замены подбирай заранее (лестница Шага 3b + `WebSearch` «аналог <товар>»),
   чтобы у пользователя был готовый выбор, а не «а что вместо?». Спрашивай одним
   проходом: по одному товару за круг — это десяток кругов на одну корзину.
2. **(a) Замена** — предложи конкретную альтернативу из этого магазина с id и ценой
   («X нет, есть похожий Y за N₽ — берём?»). Подбор и одобрение — за пользователем.
3. **(b) Другой магазин** — только с показанной **арифметикой**: это отдельный заказ
   (свои `grocery_add_to_cart` + `grocery_checkout` с другими appId/pointId) = ещё одна
   доставка + свой минимум. Считай числом: «эта позиция за X₽ тянет заказ в {сеть}:
   доставка +{цена}₽, минимум {min}₽ — одной позицией он не наберётся». Если пользователь
   согласен — **добери заказ до минимума** осмысленно (родственными позициями), а не
   балластом. **Не начинай вторую корзину, пока не оформлена и не оплачена первая** —
   запись в другой магазин СТИРАЕТ текущую (бэкенд держит одну).
4. **(c) Пропустить** — только если замены нет и другой магазин не нужен. Убери позицию,
   отметь в отчёте как не заказанную.

### Шаг 6: Сборка корзины

1. Вызови `grocery_add_to_cart(items, app_id, point_id)` с выбранными ID товаров:
   ```json
   [{"id": "248429", "count": 1}, {"id": "368285", "count": 1}, ...]
   ```
2. Вызови `grocery_cart(app_id, point_id)` — с **теми же** app_id/point_id — чтобы проверить содержимое корзины.
3. Что-то не то — правь через `grocery_set_cart`, а **не** повторным `add_to_cart`:
   он прибавляет, поэтому «добавлю ещё раз, чтобы стало правильно» удваивает позицию.
   ```
   grocery_set_cart('[{"id": "248429", "count": 0}]', app_id, point_id)   # убрать
   grocery_set_cart('[{"id": "368285", "count": 2}]', app_id, point_id)   # ровно 2
   grocery_set_cart('[]', app_id, point_id, clear=True)                   # очистить
   ```
   Тул возвращает состав корзины после изменения — сверь его, прежде чем идти дальше.
4. **Держи манифест и сверяйся с ним, а не с числом строк.** До первой записи зафиксируй
   для себя: пользовательская позиция → выбранный SKU → количество. После КАЖДОЙ записи
   перечитай `grocery_cart` и сверь построчно с манифестом — количество, а не только число
   позиций. Число строк, старый `goodsSum` и показанный `count` не доказывают, что корзина
   та, что ты собрал.
5. **`countAvailable` и блок `CART_QUANTITY_CONFLICT` — читай их.** Магазин молча исключает
   недоступный избыток из `goodsSum`, так что корзина «выглядит» верной. `grocery_cart`
   теперь пишет «в наличии N» и, при перекосе, блок с конкретными SKU. Увидел его — уменьши
   до «в наличии» или выбери замену **с согласия пользователя**; сам количество не режь
   (`grocery_set_cart` такую запись и не примет).
6. **Чужое изменение не откатывай молча.** Если корзина отличается от твоего последнего
   снапшота (например, другой хлеб) — происхождение НЕизвестно: это мог сделать сам
   пользователь. Покажи diff и спроси, а не «магазин заменил, верну назад».

### Шаг 7: Показать корзину пользователю — ОБЯЗАТЕЛЬНО перед оплатой

> **Предусловие оплаты по умолчанию: список разрешён целиком.** Ни одной строки без
> статуса — каждая найдена, заменена с согласия или осознанно выброшена. Пока есть строка
> «ещё ищу / непонятно» — `grocery_checkout` не вызывать. Чекаут — точка невозврата: до
> неё пересборка бесплатна, после доставка оплачена, и «дозаказ» остатка — это уже второй
> заказ со второй доставкой.
>
> **Пользователь может это нарушить осознанно.** Если он ЯВНО просит оформить часть сейчас
> (например: срочное — сейчас, остальное как соберётся), это его выбор, а не твоя оплошность.
> Оформляй частичный заказ — но прямо проговори, что остаток уедет ОТДЕЛЬНЫМ заказом со
> своей доставкой и минимумом, и что нужно от него ещё. Инициатива на такой сплит — от
> пользователя, не от тебя.

**Всегда** показывай полную корзину перед `grocery_checkout()`:

```
Корзина (Азбука Вкуса):
  1. Лук репчатый — 89 ₽ [СЫРОЙ]
  2. Говядина бескостная — 2473 ₽ [СЫРОЙ]
  3. Картофель — 160 ₽ [СЫРОЙ]
  4. Свёкла с майонезом — 354 ₽ [ГОТОВАЯ — сырой нет]
  ...
  Итого: 4165 ₽, доставка бесплатная, ~40 мин
```

Состав корзины — твоя часть: на кнопке будет только итоговая сумма. А вот «да/нет»
текстом не спрашивай — сумму подтвердит кнопка чекаута на шаге 8. Если пользователь
в ответ на состав говорит «изменить» (или называет другой товар/магазин) — убери,
добавь, смени магазин и покажи корзину снова.

**Если количество хоть одной строки отличается от запрошенного — покажи diff явно, до
чекаута,** и получи согласие именно на него (кнопка чекаута называет сумму, а не
построчный состав):

```
Запрошено → будет заказано
  Пелёнки: 3 → 2 (−1, остаток)
  Вода 0,5 л: 10 → 9 (−1, остаток)
  Остальное: без изменений
```

Уменьшение количества — такое же отклонение от списка, как замена SKU: «лишних позиций
нет» про урезанную строку — неправда.

### Шаг 8: Оформление + оплата

1. **Оплата: `grocery_checkout(app_id, point_id)`** — с **теми же** app_id/pointId,
   что в корзине. Тул сам доводит корзину до доставки, узнаёт финальную сумму и
   показывает пользователю кнопки «Оформить заказ на 4 165 ₽?» / «Отмена» — и
   оформляет заказ ровно на ту сумму, что была на кнопке. Своё «да/нет» текстом не
   спрашивай.

   Почему сумму называет тул, а не ты: итог из корзины — не то, что спишется.
   Весовые товары (бананы, виноград, помидоры) пересчитываются бэкендом при
   оформлении доставки, и знает результат только он.

   Нажали «Отмена» (или окно закрылось) — заказ не создан, деньги на месте.
   Повторно сам не вызывай.

2. **`dry_run=True` — предпросмотр, теперь необязательный.**
   `grocery_checkout(app_id, point_id, dry_run=True)` доводит до доставки и
   возвращает финальную сумму, **не создавая заказ и не списывая деньги**. Бери
   его, когда хочешь назвать пользователю итог и слот доставки заранее — или
   заранее поймать магазин, который сейчас не отдаёт доставку. Работает в любом
   клиенте, в том числе там, где кнопок нет.

   Сделал `dry_run` — передай его сумму в `expected_sum` при оплате. Это
   необязательная сверка: если магазин пересчитал корзину, кнопка покажет обе
   суммы («Оформить заказ на 3 700.63 ₽? (было 3 650.00 ₽ — банк пересчитал
   корзину)»), и спишется та, что на кнопке. Копируй ровно, до копейки: `3700`
   вместо `3700.63` — это не отказ, а лишняя строчка «банк пересчитал» на кнопке.

3. Счёт списания по умолчанию — тот, которым пользователь последний раз платил за
   продукты **в приложении** (не «первый счёт с балансом»). Нужен другой — возьми
   из `list_accounts()` и передай `account_id`.

   Клиент без элиситации получит «ПЛАТЁЖ НЕ ВЫПОЛНЕН»: заказ не создан, деньги на
   месте. Оформить можно только из клиента с кнопками или в приложении —
   `dry_run` там по-прежнему работает и покажет сумму.
4. Сообщи результат: ID заказа, attempt_id, итоговая сумма и **счёт списания**
   (он есть в ответе тула).
5. **Если результат UNKNOWN** («заказ мог создаться», повтор заблокирован) — НЕ повторяй вслепую.
   Скажи пользователю: «Чекаут завершился неопределённо, заказ мог создаться. Проверь заказ в приложении.»
   Затем `grocery_attempts()` (статус попытки), `grocery_order_status(order_id, app_id)` (есть ли заказ на бэкенде; тот же `app_id`, что и в checkout)
   и `diagnostics()` (redacted-трейс шагов: delivery/order/payment с http_status/blame) — найти последний
   подтверждённый шаг. Повтор (`force=True`) — только если пользователь подтвердил, что прошлого заказа нет.
6. При явной ошибке ДО создания заказа (пустая корзина, нет счёта, ошибка доставки) —
   повтор разрешён. Тул сам пишет в тексте ошибки, чья это сторона и поможет ли повтор:
   - **«ответил сам магазин»** (http 200 + код магазина) — заказа нет, деньги целы, у
     магазина нет слота доставки. Тул уже повторил запрос трижды, так что мгновенный
     повтор бесполезен: скажи пользователю, что магазин сейчас не отдаёт доставку,
     и предложи подождать 5–10 минут или взять другой магазин. Не выдавай это за свою
     ошибку и не переспрашивай состав корзины — она цела.
   - **«повтор не поможет» (4xx)** — проблема на нашей стороне: сверь app_id/point_id
     с корзиной, проверь сессию.

### Шаг 9: Отчёт

После успешного заказа:
```
✅ Заказ оформлен!
  Заказ: 400000000001
  Платёж: 100000000001 (SUCCESS)
  Сумма: 884 ₽
  Магазин: Азбука Вкуса
  Доставка: ~40 мин

Не заказано: свёкла (нет в этом магазине)
```

Если заказов вышло несколько — это отклонение от «один список = один заказ», а не норма.
Назови ЧИСЛОМ, сколько заказов и сколько раз оплачена доставка, и почему пришлось делить
(«эти позиции есть только в другой сети — второй заказ оттуда, +99 ₽ доставки»).
Пользователь согласовал это на Шаге 5/Фазе 3 — отчёт лишь фиксирует итог.

### Шаг 10: Отмена заказа (по просьбе пользователя)

`grocery_order_cancel(order_id, app_id)` отменяет оформленный заказ — оплаченный
тоже, деньги возвращаются на счёт списания. `paymentId` не нужен.

- Вердикт в ответе: `Success` — принята; `605` — заказ уже отменён; иное —
  статус НЕИЗВЕСТЕН, проверь `grocery_order_status(order_id, app_id)`.
- Передавай `app_id` — тул сам перечитает заказ и покажет фактический статус
  (только перечитанный `CANCELED` подтверждает отмену).
- Отмена — необратимое действие с реальными деньгами: если пользователь не
  назвал заказ явно, уточни какой (order_id из отчёта заказа или `grocery_attempts()`).
- Неоплаченный заказ отменять не обязательно: он отменится сам (~5 минут) и
  денег не списывает.

**Консолидация после промаха.** Если заказ уже оплачен, а потом выяснилось, что остаток
(или весь список) лучше было брать в одном другом магазине — не досылай молча второй
заказ и не отменяй молча первый. Посчитай арифметику и **покажи её пользователю**:
доплата за вторую доставку, если оставить как есть, против отмены первого заказа
(`grocery_order_cancel` — деньги вернутся) и пересбора всего в одном магазине. Решение и
явное «да» на отмену — за пользователем; `grocery_order_cancel` — только по нему.

## Флоу: длинный или смешанный список

Срабатывает не по числу строк (не «ровно 10»), а по СМЫСЛУ: список смешанный или в нём
видны сигналы конфликта сетей — позиции, которые тянут в разные магазины. Восемь таких
строк опаснее двадцати нейтральных. Здесь ломается наивный проход сверху вниз: агент
набирает часть в магазине A, оформляет, потом в магазине B обнаруживает, что в A было и
остальное, и остаётся с несколькими заказами и несколькими оплаченными доставками.
Правило одно: **сначала разреши ВЕСЬ список — где что есть и с какой доставкой, — и только
потом плати.** Сколько выйдет заказов — следствие разбора, а не выбор вслепую по ходу.

### Фаза 0. Чеклист по формулировкам пользователя

Разбери список, строка = строка пользователя, ничего не выбрасывая и не сливая молча.
По каждой отметь:

- **количество** — указано или нет (часто не указано у половины строк; это норма, не
  повод угадывать);
- **бренд** — жёсткий (конкретная марка) / мягкий («кола» — любая) / нет;
- **store-lock сигнал** — что тянет в конкретную сеть: СТМ и марки поставщиков (товар под
  собственной маркой сети или фермерская марка, которая продаётся только там); магазин,
  названный самим пользователем («…обычно беру в такой-то сети»); масс-маркет-бренд
  снеков/сладостей, которого нет в СТМ-магазине;
- **субъективное / открытое** — «получше, с хорошим составом», «самое дорогое/элитное»,
  «такое же, как обычно», «что-нибудь к чаю — предложи варианты» — это НЕ исполнять без
  пользователя.

### Фаза 1. Один консолидированный вопрос — до поиска

Не несколько остановок по ходу, а один вопрос, снимающий максимум неопределённости:

1. **Конфликт сетей**, если он виден из Фазы 0: «В списке позиции из разных сетей: часть
   есть только в одной сети (её СТМ/фермерские марки), часть — брендовые снеки, которых
   в этой сети нет. Собрать одним заказом с аналогами для выпадающих позиций, или готовы
   на несколько заказов с несколькими доставками?»
2. **Открытые/субъективные строки** — перечисли и попроси конкретику разом.
3. **Дефолты количеств** — «где количество не указано, беру 1 упаковку / 1 кг — ок?» +
   явные блокеры (например, размер, если он важен, или неоднозначная фасовка «12 штук»).

### Фаза 2. Probe покрытия — БЕЗ записи в корзину

Не выбирай магазин по первому найденному товару. Проверь покрытие списка по 2-3
магазинам-кандидатам из `grocery_stores()` **маркерами** — короткий список (5-8) тех
позиций, что различают сети:

```
grocery_plan_order('["<СТМ-товар сети>","<фермерская марка>","<брендовый снек>","<марка non-food>","<товар из названной сети>"]', app_id, point_id)
```

- Маркеры — это СТМ, названные пользователем магазины, масс-маркет-бренды, non-food.
  Нейтральное (бумага, фрукты, овощи) в маркеры НЕ бери — оно есть везде и покрытие не
  различает, только жжёт запросы. Весь список по всем магазинам не гоняй.
- Читай поле `MISSING` каждого вывода — это и есть «чего в этом магазине нет». Сведи в
  одну картину: магазин × покрыто/не покрыто, рядом доставка и минимум из `grocery_stores`.
- `MISSING` — сигнал для выбора магазина, **не приговор позиции**: поиск матчит по
  подстроке, мог не совпасть по бренду/словоформе. Финально «этого нет» решается лестницей
  из Шага 3b уже в выбранном магазине.

### Фаза 3. Отдельный вопрос про ФОРМУ заказа

Как с подтверждением перевода — форму заказа подтверждай ОТДЕЛЬНО, не подмешивая в «да/нет»
по корзине. С числами из Фазы 2:

> «Один заказ из сети A: 28 из 32 позиций. Две позиции заменю аналогами, одной не будет
> нигде. Доставка 0 ₽. — Или отдельный заказ из сети B ради той одной позиции: +199 ₽
> доставки и свой минимум. Как делаем?»

Пользователь выбирает форму (один заказ / сколько-то) здесь, до сборки корзины.

### Фаза 4. Сборка и оплата — по основному флоу

Только после согласия на форму: добей остаток лестницей замен (Шаг 3b), собери корзину
(Шаг 6), покажи (Шаг 7, с предусловием «список разрешён целиком»), один
`grocery_checkout` (Шаг 8; `dry_run` — только если называешь итог заранее). Если форма — несколько заказов, каждый оформляется и
оплачивается ПОЛНОСТЬЮ до того, как тронешь корзину следующего магазина.

## Ключевые правила

1. **Сначала разреши весь список, потом плати.** Ни одной строки без статуса (найдено /
   заменено с согласия / выброшено) на момент `grocery_checkout`. Один список → один
   заказ — мягкий дефолт; деление на несколько заказов допустимо только по согласию
   пользователя с показанной арифметикой доставок (Шаг 5 / Фаза 3), не вслепую по ходу.
2. **`grocery_checkout` — точка невозврата.** До неё смена магазина и пересборка корзины
   бесплатны; после — доставка оплачена, и остаток превращается во второй заказ со второй
   доставкой. Поэтому весь разбор списка и выбор магазина — ДО первого чекаута.
3. **Один магазин на корзину + явный контекст** — нельзя смешивать товары из разных магазинов в одном заказе. Передавай `app_id`/`point_id` (из `grocery_stores()`) в **каждый** grocery-тул; без них — `NO_STORE_CONTEXT`. Цепочка `add_to_cart → cart → checkout` должна идти с **одинаковыми** app_id/pointId. Каждый ответ начинается с `[store appId=… pointId=…]` — сверяй его. **Не пиши в корзину второго магазина, пока жива первая** — запись в другой магазин стирает текущую корзину (бэкенд держит одну на всех).
4. **Тег `likely_raw`** — предпочитай сырые ингредиенты (тег=true) если пользователь не сказал иное.
5. **Состав — твой текст, сумма — кнопка тула.** Всегда показывай корзину первой:
   на кнопке чекаута будет только итог. Своё «да/нет» на оплату не спрашивай —
   `grocery_checkout` спросит сам и оформит заказ ровно на показанную сумму.
6. **Оплати в окно ~5 минут ПОСЛЕ создания заказа** — иначе он авто-отменяется. Это про окно заказ→оплата, а не «оформляй быстрее»: собирать и разрешать список можно сколько нужно, спешка начинается только когда заказ уже создан.
7. **`custom_ordered` = приоритет** — товары которые пользователь покупал раньше, предпочитать.
8. **Количество выше остатка = блок заказа, и MCP ловит это сам.** У каждой строки
   корзины есть `countAvailable`; `grocery_cart` показывает «в наличии N», а
   `grocery_set_cart`/`grocery_add_to_cart`/`grocery_checkout` отказывают с
   `CART_QUANTITY_CONFLICT`, называя SKU, ДО обращения к доставке — заказ не создаётся,
   деньги не двигаются. Реши по каждому: уменьши до «в наличии» или замени **с согласия
   пользователя**; сам количество не режь. Это проверка по СОБСТВЕННОМУ инварианту корзины,
   не по коду магазина: сырой `HTTP 200 + код 211` на доставке — это общий отказ, что он
   значит, не подтверждено, так что не приравнивай `211` к «нет в наличии» и не расшифровывай
   код догадкой. И не лечи детерминированный дефицит повторами/монитором — повтор без
   изменения количества бесполезен.
9. **Код 268 на записи в корзину — это НЕ авария сервиса, а «корзина занята другим
   магазином».** Текст «Сервис временно недоступен» врёт: так бэкенд отвечает, когда уже
   есть корзина в другой сети. Отсюда и правило «выбирай магазин один раз» (см. п. 2-3):
   `grocery_add_to_cart`/`grocery_set_cart` сами повторят запрос в режиме сброса — и в
   ответе появится предупреждение, что корзины других магазинов очищены. **Передай это
   пользователю**, если увидишь: там могли лежать его товары. Не жди и не советуй
   «повторить позже» — само по себе это не пройдёт.
10. **КБЖУ бери из API, не выдумывай.** `grocery_good_info(good_id, …)` отдаёт состав и
   КБЖУ на 100 г и на упаковку; `grocery_rank(..., sort_by="kcal")` подтягивает их сам.
   Если структурное поле пустое — прежде чем сказать «не указано», проверь «Описание:»
   в том же ответе: часть ритейлеров пишет БЖУ текстом там, а не в отдельном поле.
   Только если и в описании ничего нет — говори «не указано»; **не подставляй
   оценку по памяти**: пользователь может считать калории или выбирать по составу, и
   выдуманное число здесь хуже, чем его отсутствие.
