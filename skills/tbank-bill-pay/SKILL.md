# Оплата счетов через T-Bank MCP

Каталог провайдеров, схема полей каждого из них и сам платёж доступны через MCP.
Пополнение телефона — это обычный P2P-перевод, см. последний раздел.

## Инструменты

| Тул | Что делает |
|---|---|
| `payment_providers()` | Список групп провайдеров (19 штук). Отсюда всегда начинай |
| `payment_providers(group, query, page)` | Провайдеры внутри группы, с поиском по названию |
| `payment_providers(provider_id, group, pages)` | **Поля для платежа** у провайдера: id поля, обязательность, подсказка, регулярка. Поиск по id сканирует до `pages` страниц (по 100), «не найден» называет границу — с `group` попадание в первую страницу |
| `payment_commission(body)` | Предпросмотр комиссии (БЕЗ денег). Заодно проверка тела банком |
| `pay_bill(provider_id, fields, amount, group, from_account)` | Оплата счёта. **РЕАЛЬНЫЕ ДЕНЬГИ** |
| `list_accounts()` | Счета + балансы (выбрать, откуда платить) |
| `get_data("subscription_bills")` | **Неоплаченные квитанции — обычно ищи здесь.** Приходит вместе с `paymentFields`, которые нужны `pay_bill` |
| `get_data("invoices")` | Выставленные счета. Часто пусто — пустой ответ НЕ значит, что счетов нет |
| `get_data("templates")` / `get_data("autopayments")` | Сохранённые платежи — там лежат id провайдеров, которыми уже платили |
| `transfer(...)` | Пополнение телефона (P2P). **Реальные деньги** |
| `payment_receipt(payment_id)` | Чек после оплаты |

## Флоу: оплатить счёт

**«Оплати ЖКХ 3400»**

1. **Найди провайдера.** `payment_providers()` → группы. Дальше
   `payment_providers(group="ЖКХ", query="мосэнерго")`.

   > Имя группы в списке и `groupId` у провайдера **не всегда совпадают** —
   > фильтр сверяется с `groupId`. «ЖКХ» и «Интернет, ТВ и телефония» тул
   > подставляет сам; если другая группа вернула пусто, это скорее всего
   > расхождение в написании, а не отсутствие провайдеров.

2. **Возьми схему полей.** `payment_providers(provider_id="…", group="…")` —
   покажет, какие поля обязательны, что они значат и какой у них формат.
   **Имена полей не угадывай.** У каждого провайдера они свои.

3. **Спроси у пользователя значения полей.** Номер лицевого счёта, период,
   показания — то, что требует схема. Не подставляй ничего по памяти.

4. **Назови провайдера, лицевой счёт и счёт списания.** Это то, чего не будет на
   кнопке, — сумму с комиссией она назовёт сама. Хочешь показать итог заранее —
   `payment_commission` с `paymentType: "Payment"`; `pay_bill` всё равно считает
   комиссию сам.

5. **Оплати — «да/нет» текстом не спрашивай.**
   ```
   pay_bill(provider_id="mosenergosb-moskva-fix",
            fields='{"account": "1234567890"}',
            amount=3400, group="ЖКХ", from_account="<счёт>")
   ```
   Тул сам проверит поля по регулярке провайдера и **откажет до отправки**, если
   что-то не сходится. Это защита от оплаты чужой квитанции — не обходи её,
   а покажи пользователю, что именно не подошло. Прошли проверку — тул покажет
   пользователю кнопки «Оплатить {провайдер}: спишется N ₽ (комиссия M ₽)?» /
   «Отмена» и отправит платёж только после нажатия. Нажали «Отмена» — деньги на
   месте, повторно сам не вызывай.

6. **Отчитайся** и предложи чек: `payment_receipt(payment_id)`.

## Пополнение телефона — это перевод, не счёт

**«Пополни телефон на 500»**

1. `list_accounts()` → выбрать счёт списания, спросить если их несколько.
2. Показать сумму и номер.
3. `transfer(500, "+7XXXXXXXXXX", "Пополнение", from_account="<счёт>")` — кнопку
   «Перевести 500 ₽ → …?» покажет сам тул.

Внутри Т-Банка это бесплатный P2P. Дальше — как в скиле переводов
(`tbank-transfer-money`): то же подтверждение кнопкой и та же обработка
«ИСХОД НЕИЗВЕСТЕН».

## Правила

1. **Поля — только из схемы провайдера.** `payment_providers(provider_id=…)` —
   единственный источник. Угаданное имя поля хуже отсутствия платежа.
2. **Неверный лицевой счёт оплачивает чужую квитанцию,** и вернуть это сложнее,
   чем перевод. Поэтому валидация обязательна, а лицевой счёт и счёт списания
   проговаривай вслух — на кнопке их нет.
3. **Подтверждает кнопка тула, а не твой вопрос.** `pay_bill` сам показывает
   пользователю итог с комиссией и платит только после нажатия — своё «да/нет»
   текстом не спрашивай. Просьба «оплати» — это запрос, а не подтверждение, но
   ответ на него — вызов тула, а не переспрашивание. Клиент без элиситации
   получит «ПЛАТЁЖ НЕ ВЫПОЛНЕН»: объясни, что платить нужно из клиента с
   кнопками или в приложении, текстовое подтверждение вместо кнопки не изобретай.
4. **Сумму не угадывай** — спроси или возьми из счёта. Проверяй ОБА места: `get_data("subscription_bills")` (там квитанция вместе с `paymentFields`) и `get_data("invoices")`. Пусто в одном ничего не доказывает.
5. **ИСХОД НЕИЗВЕСТЕН — не повторяй вслепую.** Проверь
   `list_operations(<счёт>, days=1)` и только при отсутствии платежа повторяй с
   `force=True`.
6. **После оплаты проверь `list_operations()`.** Подтверждение исхода — всегда
   по операциям, а не по ответу тула.
7. **«ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ» (WAITING_CONFIRMATION).** Если банк держит платёж до
   второго фактора — деньги ещё не ушли, но платёж висит. Не повторяй `pay_bill`
   (будет второй висящий платёж); возьми код из SMS/пуша и вызови
   `confirm_payment(attempt_id, otp)`, исход проверь через
   `payment_status(attempt_id)`. `confirm_otp` — только для логина, платёж им не
   подтвердить.
