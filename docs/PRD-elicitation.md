# PRD — Элиситация в T-Bank MCP

**Статус:** фазы 0–5 реализованы · **Владелец:** neondelph · **Обновлён:** 2026-08-14
**Трекинг:** ВСЕ фазы 0–5 в коде. Тесты — `tests/test_elicitation.py` (фазы 0–1) и
`tests/test_elicitation_flows.py` (фазы 2–5, пикеры/гейты/логин-цепочка). Осталось
ТОЛЬКО живая приёмка в Hermes/Telegram (§12): она снимает два непроверенных
момента — рендер пустой формы гейта (`_TransferGateForm`; запасной ход —
поле `confirm: bool`) и рендер enum-пикера (`json_schema_extra["enum"]` →
кнопки/селект). Код деградирует в текстовый флоу без элиситации, так что оба
блокера — про UX в клиенте, не про корректность.

---

## 1. Одной фразой

Заменить текстовые «подтверди с пользователем» на **первоклассные диалоги
элиситации** (форма/кнопки прямо в клиенте), сохранив полную обратную совместимость:
если клиент элиситацию не объявил — поведение ровно как сейчас.

## 2. Проблема

Сейчас подтверждение и дизамбигуация идут «через агента текстом»:
- `confirm_payment` возвращает строку «ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ…», агент просит код,
  пользователь диктует, агент повторно зовёт тул с `otp`.
- Выбор банка СБП (`transfer_sbp_resolve` вернул несколько), выбор `from_account`,
  недостающее назначение платежа — всё это агент «додумывает» или переспрашивает
  свободным текстом.

Минусы: подтверждение денег зависит от рассуждения LLM, а не от детерминированного
ответа человека; OTP летит через контекст модели; UX рыхлый. Заметка проекта
`transfer-confirmation-explicit` прямо требует отдельного явного «Перевести / Отмена».

## 3. Вводные (проверено, не предположения)

- **Элиситация доступна на текущем пине `mcp>=1.2,<2`.** FastMCP отдаёт
  `Context.elicit(message, schema)` (и `elicit_url`, и `report_progress`).
  Мигрировать на 2.0 **не нужно**.
- **Клиент пользователя — Hermes (NousResearch) через Telegram.** Он поддерживает
  **form-mode** элиситацию: маршрутизирует её в approval-поверхность — кнопки/промпт
  прямо в чате Telegram. Включено по умолчанию, таймаут **300 с**.
- **URL-mode (`elicit_url`) Hermes ОТКЛОНЯЕТ.** Значит форма/кнопки — да, внешняя
  ссылка — нет.
- **`ctx.elicit` — async.** Наши тулы почти все sync (114 `def`, async только
  `grocery_checkout`). Тулы, которые будут элиситить, придётся сделать `async` и дать
  им параметр `ctx: Context`.
- **Элиситация согласуется как capability клиента на init.** Проверять наличие через
  server session (`ServerSession.check_client_capability(ClientCapabilities(
  elicitation=ElicitationCapability()))`) и падать в fallback, если не объявлена.
- **MCP Apps (`ui://` виджеты) — вне scope:** в Telegram-чате iframe не рендерится, и
  это только 2.0. См. §9.

## 4. Цели / Не-цели

**Цели**
1. Денежное подтверждение — детерминированный диалог «Перевести / Отмена» + ввод OTP
   в клиенте, а не текст через агента.
2. Полная обратная совместимость: нет элиситации у клиента → нынешний текстовый флоу
   байт-в-байт.
3. Ноль регрессий по безопасности: OTP не логируется; `decline`/`cancel`/timeout
   деньги НЕ двигают.

**Не-цели**
- Миграция на mcp 2.0. Пин `<2` остаётся.
- MCP Apps / `ui://` / любые UI-виджеты.
- URL-mode элиситация (`elicit_url`) — Hermes её не берёт.
- Перелопачивать все 114 тулов в async. Трогаем только те, где элиситация даёт смысл.

## 5. Требования

### Функциональные
- **F1. Capability-детект + fallback.** Перед любым `ctx.elicit` проверить, объявил
  ли клиент элиситацию. Не объявил (или `ctx` отсутствует, напр. в тесте/headless) →
  вернуть текущий текстовый ответ. Никакой жёсткой зависимости.
- **F2. Подтверждение перевода.** Для крупного/рискованного `/v1/pay`
  (`transfer_requisites`, `transfer`, `pay_bill`): диалог «Перевести N₽ → <получатель>
  [Перевести / Отмена]» ДО отправки. `decline`/`cancel` → ничего не отправляем.
- **F3. Ввод OTP.** Когда `/v1/pay` вернул `WAITING_CONFIRMATION`, `confirm_payment`
  элиситит форму «Код из SMS (`codeLength` цифр)». `accept` → код уходит в
  `secretValue`; `decline`/`cancel`/timeout → платёж остаётся висящим, состояние не
  портим.
- **F4. Дизамбигуация (вторая волна).** `transfer_sbp_resolve` (несколько банков),
  выбор `from_account` при нескольких счетах — option-select; недостающее назначение
  платежа — форма.
- **F5. Порог.** Диалог «Перевести/Отмена» не для каждого перевода, а от порога суммы
  (конфиг, напр. `TBANK_CONFIRM_ABOVE`, дефолт обсудить) — чтобы мелкие P2P не душить.

### Нефункциональные
- **N1. OTP-гигиена.** Код из формы идёт только в `secretValue` (ключ содержит
  `secret` → редактор режет). Нигде не журналируется/трейсится. (Уже гарантировано,
  не сломать.)
- **N2. Таймаут.** Hermes даёт 300 с. Истёк → трактуем как `cancel`: деньги не
  двигаем, говорим, что подтверждение не получено, платёж висит.
- **N3. `decline`/`cancel` семантика.** Различать «пользователь отказался» (штатно,
  без паники) и ошибку; для висящего платежа оставлять `waiting_confirmation`.
- **N4. Схема тула не должна измениться для агента.** FastMCP исключает
  `Context`-параметр из JSON-схемы; проверить, что `trace.wrap` (`__wrapped__`) это
  сохраняет — иначе `ctx` протечёт в схему инструмента.
- **N5. Пин.** `mcp>=1.2,<2` не трогаем (см. `test_dependency_pins.py`).

## 6. UX-флоу (целевые)

**Крупный перевод по реквизитам**
```
transfer_requisites(...) 
  → [сумма ≥ порога и есть capability]
      elicit «Перевести 150 000 ₽ → ООО «Пример»? [Перевести] [Отмена]»
        Отмена → «Перевод отменён, деньги на месте.»  (POST не делаем)
        Перевести → POST /v1/pay
  → WAITING_CONFIRMATION
      elicit форма «Код из SMS (4 цифры): [____]»
        Отмена/таймаут → «Код не введён, платёж висит; payment_status(...)»
        код → /v1/confirm → «Отправлено. paymentId=…»
```

**Без элиситации (любой другой клиент / тест)** — как сейчас: две строки-инструкции
(«подтверди сумму…», затем «продиктуй код и вызови confirm_payment(attempt_id, otp)»).

## 7. Дизайн / реализация

- **Хелпер** `server._elicit_or(ctx, message, schema, *, fallback)`:
  проверяет capability; есть → `await ctx.elicit(...)`, мапит `action`; нет/`ctx is
  None` → возвращает сентинел «нет элиситации», тул уходит в текстовый флоу. Один
  источник правды для всех тулов.
- **Async-конверсия** только затронутых тулов (`confirm_payment` первым; затем крупный
  `transfer*`/`pay_bill`). Паттерн async-тула уже есть (`grocery_checkout`).
- **`confirm_payment(attempt_id, otp="", ctx=None)`** — `otp` становится
  опциональным: передан явно → как сейчас; пуст и есть элиситация → форма.
- **Pydantic-схемы** — только примитивы (ограничение form-mode): OTP = `{code: str}`;
  подтверждение = enum/bool; выбор банка/счёта = enum по индексам.
- **Порог/конфиг** — env, чтобы не хардкодить поведение.

## 8. Rollout по фазам

Четыре паттерна из фаз 0–1, из которых собирается всё остальное: **гейт**
(пустая схема, Accept-кнопка = действие), **форма** секрета/недостающего ввода,
**пикер из N** (см. ограничение на enum ниже), **force/dry_run → диалог**
(отказ «повтори с force=True» становится вопросом человеку).

**Ограничение SDK (проверено на 1.28.1):** валидатор элиситации ОТКЛОНЯЕТ
`Literal`/`Enum` в схеме, но `str`-поле с `Field(json_schema_extra={"enum": […]})`
проходит и доносит enum до клиента. Все пикеры строятся так; маппинг
«подпись → pointer_link_id/account id» живёт на сервере в рамках вызова.

   - `transfer` (P2P): резолв получателя переносится в async-обёртку ДО

   - Сумма: «В QR суммы нет — передай amount=» → форма `{amount: float}`.

   - `messenger_send`: гейт «Отправить в поддержку: „{text[:80]}"?» — необратимо,

   - `grocery_checkout`: при элиситации и пустом `expected_sum` — dry-run-квота в
     `to_thread` → гейт «К оплате {total} ₽?» → повтор тела с

6. ✅ **Фаза 5 (логин).** Сделано. SMS-код и PIN логина — прямой аналог

   credentials в `elicit_url`, который Hermes отклоняет; form-mode означает
   «пароль в истории Telegram-чата». Пароль остаётся за `login_cli.py`.
   `REAUTH_REQUIRED` требует полной цепочки с паролем — вне scope по той же
   причине.

Порядок внутри фаз — по цене/ценности: `messenger_send` и `ticket_pay` дешёвые,
`transfer` самый ценный, `pay_bill` — средний рефакторинг. Фазы 2–3 висят на
проверке рендера enum в Hermes (см. §12): до неё пикеры не проектировать.

## 9. Вне scope (и почему)

- **MCP Apps / `ui://`** — не рендерятся в Telegram-чате; только 2.0 + webview-хост.
- **Миграция на mcp 2.0** — нулевая выгода для headless-банка, форк `httpx2` = риск.
- **URL-mode элиситация** — Hermes отклоняет.
- **Пагинация, уточнение запросов, выбор мест/слотов/магазина** («передай
  limit=N», «уточни query», `cinema_seats`, `grocery_stores`, подстановки
  `grocery_plan_order`) — переговоры по содержимому, где свободный текст агента
  богаче формы из примитивов. Form-mode здесь ухудшил бы UX.
- **`grocery_add_to_cart`/`set_cart`** (корзины других магазинов стираются
  молча): честный гейт требует pre-check чужих корзин, эндпоинта для которого
  нет — вернуться, если найдётся.
- **Travel/shop** — read-only by design; **`card_limits`** — нет сеттера;
  **`bank_documents`** — нет заказа справок.
- **MyT** — отдельный репозиторий, тул с паролем там запрещён политикой;
  элиситация SMS-кода — отдельная работа в том репо.

## 10. Тесты (executable, как везде в репо)

- `capability отсутствует` (ctx=None или без elicitation) → тул отдаёт нынешний текст,
  ничего не элиситит, деньги не двигаются.
- `accept` → код уходит в `secretValue`, `/v1/confirm` зовётся, journal `paid`.
- `decline` / `cancel` / timeout → платёж остаётся `waiting_confirmation`, деньги не
  двинуты, сообщение честное.
- OTP из формы **отсутствует во всех логах** (attempts/events/calls).
- Схема тула, которую видит агент, **не** содержит `ctx` (N4).
- Регресс: существующий флоу с явным `otp=` работает как прежде.

## 11. Риски / открытые вопросы

- **R1.** `trace.wrap` + `ctx`-параметр + async: убедиться, что схема и трейс не
  ломаются (N4). — проверить на пилоте.
- **R2.** Порог суммы для «Перевести/Отмена»: значение по умолчанию? (обсудить)
- **R3.** Таймаут 300 с vs время жизни SMS-кода/`operationTicket` — если тикет
  протух за время ожидания формы, `/v1/confirm` даст ошибку → нужен внятный текст +
  «запроси код заново в приложении».
- **R4.** Headless/автономный прогон Hermes: элиситация может авто-отвечаться хуком —
  для денег это НЕ то же, что человек нажал кнопку. Решить, требуется ли для money
  path «живой» ответ (возможно, помечать такие элиситации).

## 12. Критерии приёмки

- В Hermes/Telegram крупный перевод показывает кнопки «Перевести/Отмена», а
  подтверждение — форму ввода кода; отказ и таймаут деньги не двигают.
- В любом другом клиенте/в тестах поведение идентично текущему.
- Вся сюита зелёная; OTP нигде не логируется; пин `<2` на месте.
- Живая приёмка заодно отвечает на два вопроса, на которых висят фазы 2–4:
  (1) рендерит ли Hermes ПУСТУЮ форму гейта (запасной ход — поле
  `confirm: bool`); (2) рендерит ли enum из `json_schema_extra` как
  кнопки/селект — без этого пикеры фаз 2–3 не проектировать.
